## Before the mechanics: what a risk matrix is and isn't

A likelihood × impact matrix is a **communication device**, not an analysis. Multiplying
two ordinal scores is mathematically dubious — "3 × 4" is not twice "2 × 3", because the
underlying scales aren't linear and aren't in the same units. Matrices reliably produce
confident-looking numbers from guesses.

That is a reason to lean on derived values wherever they exist, not a reason to skip the
register. The organisation asks for one, and a register that is *mostly derived from
measured data* is a genuine improvement on one that is entirely gut-feel.

Hence the central distinction in this document:

| | Static risk | Dynamic risk |
|---|---|---|
| Example | "The codebase has poor test coverage" | "Item #4412 will not land this sprint" |
| Changes | Slowly, by decision | Daily, by itself |
| Scored by | Judgement, reviewed periodically | **Derived from a measure we already collect** |
| Reviewed | Monthly delivery review | Weekly flow review — often resolved before it's ever written down |
| Lives | In the register | In the flow charts; only *escalated* entries reach the register |

**Dynamic risks should not be hand-scored.** If a measure in `docs/02-measures.md`
already answers "how likely" and "how bad", reading it off is better than a workshop.

## 1 · The scoring scale

### Impact — in days, not adjectives

The playbook already gives stakeholders dates as probabilistic ranges
(`docs/06-stakeholder-communication.md`). So impact is expressed in the same unit they
already receive: **how far does the 85% date move if this risk lands?**

| Score | Impact | Meaning |
|---|---|---|
| 1 | Negligible | No forecast movement. Absorbed inside existing variability |
| 2 | Minor | 85% date moves ≤ 1 week |
| 3 | Moderate | 85% date moves 1–3 weeks |
| 4 | Major | 85% date moves 3–8 weeks, or a dependent commitment is missed |
| 5 | Severe | 85% date moves > 8 weeks, or the outcome is no longer achievable |

For a risk with no delivery-date consequence (a security exposure, a compliance gap),
score impact on your organisation's existing severity scale and say which scale you used
in the entry. Don't invent a translation.

### Likelihood — measured where it can be

| Score | Likelihood | Static risk (judged) | Dynamic risk (derived) |
|---|---|---|---|
| 1 | Rare | Not seen here | Observed in < 5% of comparable items |
| 2 | Unlikely | Seen elsewhere, not here | 5–20% |
| 3 | Possible | Happened once | 20–50% |
| 4 | Likely | Happens periodically | 50–80% |
| 5 | Near-certain | Happens most iterations | > 80%, or already occurring |

**"Derived" means from your own history, not from instinct.** Once you have a few months
of data, most dynamic likelihoods are a query: *of items that breached the 85th
percentile band, what share went on to breach the 95th?* That number is your likelihood
score for "this item will overrun", and it is specific to your team rather than borrowed.

Until you have that history, score it 3 and write **"(estimated — no baseline yet)"** in
the entry. An honest placeholder beats a confident invention, and it creates a visible
queue of things to replace once `teams/<team>/baseline.md` is populated.

## 2 · Tiers

Score = likelihood × impact, 1–25. The tiers deliberately reuse the escalation ladder
already in `docs/04-policies.md` for aging items, so a risk tier means the same thing as
an aging band and triggers the same response:

| Score | Tier | What happens | Mirrors |
|---|---|---|---|
| 1–6 | **Watch** | Logged and visible. No action required | Item past the 70th percentile — flagged, no action |
| 8–12 | **Act** | Named owner and a next action before the review ends | Item past the 85th — named action and owner |
| 15–25 | **Escalate** | Raised to the delivery lead, then the sponsor. Mitigate, accept explicitly, or stop the work | Item past the 95th — unblock, split, or explicitly stop |

Three tiers, not five. Red/amber/green would be a fourth vocabulary in a repo that
already has percentile bands and aging tiers.

**Any single 5 on impact is at least Act, whatever its likelihood.** A severe outcome at
low probability is exactly the case a multiplied score hides — this is the main known
failure of matrices, and the override is the standard remedy.

## 3 · Dynamic risks: where each one comes from

Every row below is generated by a measure the playbook already collects. The register
entry is written **only if it reaches Act or Escalate** — a Watch-tier dynamic risk is
just a number on a chart, and copying it into a spreadsheet adds nothing.

| Signal | Existing measure | Risk entry it creates | Likelihood from | Impact from |
|---|---|---|---|---|
| Item past the 85th band, still open | Work item age (`02`, measure 1); age limits (`04`) | "#____ will not land this sprint" | Share of past-85th items that went on to breach the 95th | Days of forecast movement if it slips |
| Item past the 95th band | Age limits (`04`) | "#____ is stalled; value or readiness in doubt" | Near-certain — already occurring (5) | As above, plus the cost of the decision to stop |
| Arrivals exceeding departures, 2+ weeks | WIP and throughput (`02`, measures 2–3) | "Cycle time will rise across the board" | Little's Law — derived, not guessed | Model it: rerun the forecast at projected WIP |
| Forecast 85% date moving out, 2+ refreshes | Monte Carlo (`04`, forecasting) | "Date will continue to drift" | Direction and size of the last 3 refreshes | The drift itself, extrapolated one refresh |
| Run of actuals beyond the 85th percentile | Forecast calibration (`04`; `12`) | "Capacity regime has changed; forecasts are stale" | Near-certain if 3+ in a row (5) | Whole-forecast, until the window is reshortened |
| Same blocker reason 2+ weeks, or across teams | Blocked days by reason (`04`) | "Systemic constraint in ____" | Recurrence rate in the blocked log | Blocked days per month × affected items |
| Time in waiting states exceeding time in active states | **Wait-state breakdown** (`02`, supporting measures) | "Delay is downstream of development (H5)" | Share of items affected | Days per item in the offending state |
| Backlog wait 95th percentile rising | Backlog wait (`02`, measure 5) | "Intake exceeds capacity, or the backlog holds work nobody intends to do" | Trend over 3 months | Lead-time impact on the oldest cohort |
| Unplanned work above ~20% of throughput | Unplanned work % (`02`) | "Forecast history is unrepresentative; forecasts are optimistic" | Measured share | Recompute the forecast including unplanned work — the delta *is* the impact |
| Expedites more than ~2/sprint | Expedite frequency (`02`, `04`) | "Urgency is running the system" | Observed rate | Days added to everything the expedites displaced |
| People allocated below 100% to one team | H7 (`01`) | "Throughput history describes a team that no longer exists" | Count of fractional people | Cycle-time difference between whole and split allocations (`11`) |

### On flow efficiency

The brief that requested this document named *"flow efficiency dropping"* as a dynamic
signal. It is deliberately **not** in the table above.

`docs/02-measures.md` lists flow efficiency under what to stop measuring: gameable, needs
suspiciously precise activity data, and conflates two distinct problems — long waits and
slow work — into one number. Using it here would reintroduce a metric the playbook
retired, and would let a risk be scored against a number nobody trusts.

The **wait-state breakdown** row carries the same signal with none of those problems, and
it names the queue that needs attacking rather than returning a ratio.

### On stage-gating

The brief also asked to cross-reference a stage-gating section. **There isn't one**, and
the omission is deliberate rather than accidental: `docs/09-sprint-goals.md` retires the
committed outcome, and a gate is a commitment checkpoint. Cross-referencing a section
that doesn't exist would be the clearest possible way to introduce the second,
disconnected vocabulary this document is meant to avoid.

Three things in the playbook do the job a gate is usually meant to do, and dynamic risks
map to them instead:

| Gate-like control | Where | What it actually gates |
|---|---|---|
| Definition of Started | `04-policies` | Work cannot begin until it can genuinely progress |
| Intake limit and the "not yet" queue | `11-demand-and-intake` | Nothing new starts until something finishes |
| Aging escalation ladder | `04-policies` | An item cannot age indefinitely without a decision |

If the organisation requires formal gates for governance reasons, record them as static
risks about the gate itself ("gate review scheduled after the 85% date") rather than
building a parallel control system.

## 4 · Review cadence and ownership

Slotted into the existing rhythm in `docs/03-operating-cadence.md`. No new meetings.

| When | Who | What happens |
|---|---|---|
| **Daily** (standup) | Team | Dynamic risks surface as answers to "what is stopping this finishing today?" Most are resolved here and never become entries |
| **Weekly** (flow review, 30 min) | Delivery lead facilitates | Walk aged items; anything reaching Act gets an owner and a next action. New dynamic entries are raised here |
| **Monthly** (delivery review, 90 min) | Delivery lead owns the register | Every static risk reviewed. Escalate-tier entries reviewed regardless of tier. Closed and accepted entries confirmed |
| **Quarterly** (recalibration) | Delivery lead + team leads | Re-derive likelihood percentages from the quarter's data. Refresh impact bands against the current forecast. Delete entries nobody has acted on |

### Ownership

- **The delivery lead owns the register** — that it exists, is current, and is reviewed.
- **Each entry has a named individual owner**, never a team. "The team" owning a risk
  means nobody owns it.
- **The owner is whoever can act**, not whoever raised it. A risk about environments is
  owned by whoever can change the environments, even if a developer found it.
- **Dynamic entries are owned by the team** while at Act tier and transfer to the
  delivery lead on escalation — mirroring the aging ladder, where the 95th percentile
  escalates to you.

### Lifecycle

```
raised → Watch → Act → Escalate → ┬→ mitigated → closed
                                  ├→ accepted (reviewed quarterly)
                                  └→ work stopped
```

**Escalated.** Reaching Escalate means the score crossed 15, *or* impact hit 5 at any
likelihood. On escalation the entry gets a date by which a decision will be made — not
a date by which it will be fixed. An escalation without a decision date becomes
furniture.

**Downgraded.** Re-score at review, never between. A risk downgraded because the measure
moved keeps the old score in its history — a risk that oscillates between tiers is
itself a finding, and usually means the score was tracking noise rather than the system.

**Closed.** Only when the risk can no longer occur — the cause was removed, or the work
it threatened is done. "We haven't seen it recently" is not closed; it is Watch.

**Accepted.** An explicit decision not to mitigate, with a named accepter, reviewed
quarterly. This is the most underused status in most registers: teams carry mitigations
nobody intends to perform because nobody will say out loud that the risk is tolerable.
An accepted risk is honest; a stale open one is not.

**Escalated to whom.** The delivery lead first, then the sponsor. Where a risk is outside
a team's control — allocation, demand, priority churn — escalation is the whole point,
and `docs/11-demand-and-intake.md` is the conversation it feeds.

## 5 · The register

One row per risk. Dynamic entries appear here only at Act tier or above.

| ID | Risk description | Type | Likelihood (1–5) | Impact (1–5) | Score | Tier | Owner | Source measure | Mitigation | Status | Last reviewed |
|---|---|---|---|---|---|---|---|---|---|---|---|
| R-001 |  | static / dynamic |  |  |  | Watch / Act / Escalate |  | — or `02` measure |  | open / accepted / mitigated / closed |  |
| R-002 |  |  |  |  |  |  |  |  |  |  |  |
| R-003 |  |  |  |  |  |  |  |  |  |  |  |

### Writing a good entry

**Description states the consequence, not the condition.** "Poor test coverage" is a
condition. *"Low coverage in the payments module means regressions reach production
undetected"* is a risk — it says what goes wrong, which is what makes it scorable.

**Source measure is mandatory for dynamic entries.** If you cannot name the measure the
score came from, it is a static risk being scored by feel — label it static and be honest
about it.

**Mitigation is an action with an owner, not an intention.** "Improve test coverage" is
an intention. *"Add contract tests to the payments module — Sarah, by the 30th"* is a
mitigation.

**One risk per row.** A description containing "and" is two entries with two owners.

## Worked example

| Field | Value |
|---|---|
| ID | R-014 |
| Description | Thin data in the dev environment means pagination and volume behaviour ship untested |
| Type | Dynamic |
| Likelihood | 5 — occurred 3 times in 4 weeks across 2 teams |
| Impact | 3 — 85% date moved ~1.5 weeks across affected items; plus untested volume behaviour reaching production |
| Score | 15 |
| Tier | **Escalate** |
| Owner | Platform lead (whoever can change it, not whoever found it) |
| Source measure | Blocked days by reason (`environment`); friction log (`13`) |
| Mitigation | Seeded dataset in the shared dev environment — decision date agreed, not fix date |
| Status | Open |

Note where that entry came from: not a risk workshop, but three answers to *"what is
stopping this finishing today?"* in three different flow reviews, counted rather than
absorbed (`docs/13-friction-and-delay.md`). **That is the register working as intended —
it aggregates what the cadence already surfaces, rather than asking people to imagine
what might go wrong.**
